# Stream relay service

Небольшой HTTP-сервис, который отдаёт m3u/m3u8-плейлист, проксируя (без транскода) исходный плейлист из `M3U_SOURCE_URL`. Не связан с ботами из корня репозитория — отдельный процесс, отдельный деплой.

Он же выдаёт пропуска в комнаты LiveKit для совместного просмотра в
[MatchLive](https://github.com/Aloews/sherlock-tv) — см. раздел ниже. Два
разных дела в одном сервисе по одной причине: у MatchLive сервера нет вовсе,
это статическая страница, а подписывать пропуск можно только там, где лежит
секрет.

## Переменные окружения

- `M3U_SOURCE_URL` — обязательная, URL исходного m3u/m3u8-плейлиста.
- `STREAM_ACCESS_TOKEN` — опциональная, если задана, `/playlist.m3u8` требует `?token=...`.
- `PLAYLIST_CACHE_TTL_MS` — опциональная, по умолчанию `30000` (кэш плейлиста в памяти, чтобы не дёргать источник на каждый запрос).
- `PORT` — задаётся платформой автоматически (Railway).

Для совместного просмотра (всё опционально; без первых трёх `/livekit-token`
честно отвечает `503`, а релей плейлиста работает как работал):

- `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET` — ключ и секрет проекта LiveKit.
- `LIVEKIT_URL` — адрес сервиса, `wss://…`. Уходит клиенту вместе с пропуском.
- `LIVEKIT_ACCESS_TOKEN` — опциональная, закрывает саму выдачу пропусков (`?token=…`), ровно как `STREAM_ACCESS_TOKEN` закрывает плейлист.
- `LIVEKIT_TOKEN_TTL_SECONDS` — опциональная, по умолчанию 14400 (4 часа: матч с добавленным временем и разговором после).

## Эндпоинты

- `GET /playlist.m3u8` (алиас `/playlist.m3u`) — отдаёт плейлист.
- `GET /healthz` — проверка живости.
- `GET /livekit-token?room=<код>&name=<имя>` — пропуск в комнату совместного просмотра.

### Совместный просмотр

```
GET /livekit-token?room=abc123xyz&name=Вася
→ { "url": "wss://…", "token": "eyJ…", "room": "abc123xyz", "identity": "tv-…", "ttl": 14400 }
```

Коды ответа: `400` — негодный код комнаты; `403` — не сошёлся
`LIVEKIT_ACCESS_TOKEN`; `503` — сервис не настроен.

⚠️ **Чем закрыта комната и чем она НЕ закрыта.** Проверки «кто ты» здесь нет и
взяться ей неоткуда: Telegram отдаёт подпись только приложениям, у которых есть
сервер бота. Значит, пропуск получает всякий, кто знает **код комнаты**, — код
и есть ключ. Поэтому код генерирует приложение случайным (не человек по
памяти), а `LIVEKIT_ACCESS_TOKEN` закрывает выдачу целиком, если комнаты не
должны заводиться посторонними.

⚠️ **Права в пропуске узкие, и клиент их не расширит.** Войти, публиковать
микрофон и камеру, слать сообщения комнаты — и всё. Ни `roomAdmin`, ни
`roomList`, ни `roomCreate`, ни демонстрации экрана: список источников решает
сервер. Это проверяется тестом, который смотрит и на то, чего в пропуске быть
не должно.

⚠️ **CORS обязателен.** Приложение живёт на другом домене (Vercel), браузер
шлёт preflight и без `access-control-allow-origin` выбрасывает даже успешный
ответ. На этом же релее так уже ломался плейлист.

## Деплой на Railway (отдельный сервис в том же проекте/репозитории)

1. В том же Railway-проекте, где уже крутится management-бот, **New Service → Deploy from GitHub repo** → тот же репозиторий `sherlock-ai-bot`.
2. В настройках нового сервиса выставить **Root Directory** = `stream-service` (Railway найдёт здесь свой `Dockerfile`, не трогая корневой).
3. Добавить переменные: `M3U_SOURCE_URL` (обязательно), при желании `STREAM_ACCESS_TOKEN`.
4. Сгенерировать домен (**Settings → Networking → Generate Domain**).
5. Проверить: `curl https://<домен>/healthz` → `ok`, `curl https://<домен>/playlist.m3u8` → содержимое плейлиста.
6. В приложении Sherlock Scholes использовать `https://<домен>/playlist.m3u8` (+ `?token=...`, если включена авторизация) как источник потока.
